# Week 7：与 UI-TARS、Claude Computer Use 的差距分析

查阅日期：2026-09-09

## 结论

本项目已经具备一个小型但完整的 GUI Agent 闭环：截图与 OCR、显式计划、结构化动作、执行后验证、有限重试与重规划，以及默认不操作真实桌面的安全策略。它更接近“可审计的本地工程原型”，而 UI-TARS 是用大规模 GUI 数据和在线轨迹训练的端到端原生模型，Claude Computer Use 则是由模型、Anthropic 定义的客户端工具集和调用方运行环境共同组成的产品能力。

Week 7 正式合成评测中，基础 OCR 条件在三个分辨率共成功 5/60（8.3%）；oracle 观察条件成功 1/20（5%），说明当前主要短板不能简单归因于 OCR。最大的能力差距是多步规划输出的稳定性、原生视觉定位训练、真实桌面轨迹规模和跨应用长期恢复，而不是缺少鼠标键盘执行函数。

## 架构对照

| 维度 | 本项目 | UI-TARS（v1） | Claude Computer Use（当前官方文档） |
|---|---|---|---|
| 感知 | 截图加 EasyOCR 文本框；模拟评测另有 oracle 模式 | 端到端模型只接收截图，以大规模 GUI 截图训练上下文感知与元素描述 | 模型接收调用方返回的截图；桌面由调用方提供和控制 |
| 定位 | OCR 框中心点；模型动作使用 0–999 相对坐标网格，执行前转换为像素 | 通过大规模动作轨迹学习原生 grounding | 工具调用可直接携带截图像素空间坐标，例如 `left_click` 的 `coordinate` |
| 动作空间 | 7 类严格 Pydantic 动作：click、type、hotkey、scroll、drag、wait、finish | 将不同平台动作标准化到统一动作空间 | `computer_toolset_20260801` 提供 17 个成员工具，包括 screenshot、left_click、type、zoom；调用方负责执行 |
| 规划 | 显式 `TaskPlan`、`PlanProgress` 和当前活动步骤，便于检查与测试 | System-2 多步推理，包括任务分解、反思和里程碑识别 | 模型按 `tool_use` 循环提出动作；官方接口不要求暴露本项目这种固定 `TaskPlan` 对象 |
| 记忆 | 提示中保留完成步骤、失败原因和最近 3 条执行结果；无跨任务长期记忆 | 使用反思式在线轨迹收集与迭代训练，让错误经验进入后续训练 | 当前会话中的截图、工具调用和工具结果由调用方回传；持久记忆不是 Computer Use 工具本身自动提供的能力 |
| 恢复 | 规则验证、有限 retry、最多 1 次 replan，并有重复动作停止 | 由模型的反思、错误修正和迭代训练支持 | 模型收到每次 `tool_result` 后继续；循环、错误返回和停止条件由调用方实现 |
| 安全 | 默认 dry-run；真实桌面逐动作要求输入固定确认词；动作范围和参数白名单 | 所查 UI-TARS 论文摘要与架构说明未报告等价的逐动作人工确认机制 | 官方建议隔离 VM/容器、最小权限、域名白名单、敏感动作人工确认，并说明有提示注入检测层 |
| 训练 | Qwen3-VL 本地基座；本项目仅用 100 条 ScreenAgent 样本做 QLoRA 实验 | 大规模 GUI 截图与动作轨迹、System-2 推理数据、数百台虚拟机生成的反思式在线轨迹 | 训练数据与方法为专有信息，官方 Computer Use 文档未公开可复现训练配方 |

上表的 UI-TARS 描述来自论文摘要所列四项关键设计；Claude 的工具数量和执行责任以 2026-09-09 的官方文档为准，后续版本可能变化。

|---|---:|---|---|

| Claude Computer Use 官方文档 | 文档公开工具协议、安全建议和调用方职责，没有提供可与本项目复现条件一致的成功率 | 可用于比较产品架构、动作接口和安全边界 | 不能从工具文档推导模型在 OSWorld 或本项目任务上的成绩 |

## 不可比声明

UI-TARS 的数字来自 OSWorld、AndroidWorld 等公开基准，WebArena 又有自己的功能网站、任务分布和评分器；本项目的数字来自 5 个本地原型应用上的 20 项合成任务，每个条件 `n=20`。它们在任务分布、环境真实度、应用数量、模型版本、最大步数、评分器、样本量和硬件上都不同。

因此，任何把这些百分比放在同一张排名表中的横向比较都无效。本节的用途是定位能力差距和估算补齐工作，而不是宣称本项目优于或落后某个公开分数多少个百分点。

## 差距清单与补齐代价

以下工期是本项目的工程估算，不是论文结论。假设由 1–2 名熟悉 Python、VLM 训练和桌面自动化的工程师完成；数据授权、GPU 排队和第三方环境兼容可能让实际时间更长。

| 差距 | 目前证据 | 若要补齐需要什么 | 粗略投入 |
|---|---|---|---:|
| 原生视觉 grounding | 依赖 OCR 框和提示词坐标；oracle 并未提高成功率，但它不能替代真实定位训练 | 收集控件框/点击点数据，加入多分辨率 grounding 损失与离线 ScreenSpot 类评测；保留 OCR 作为辅助而非唯一定位来源 | 4–8 人周，加中等规模 GPU 训练 |
| 规划输出稳定性 | adapter 条件 20/20 为 `planner_output_invalid`；基础条件也大量停止 | 扩大有效多步轨迹，做严格 schema-aware SFT，增加输出修复但不掩盖错误，并建立计划/动作两级离线评测 | 4–8 人周，加数据清洗与训练轮次 |
| 大规模真实轨迹 | 当前训练仅抽取 100 条 ScreenAgent 样本，Week 7 主评测是合成桌面 | 建立隔离 VM 池、可重置任务、轨迹录制、隐私清理、许可证清单和人工复核；规模至少从数百条有效多步轨迹起步 | 6–12 人周，另需 VM/GPU 成本 |
| 长程记忆与反思 | 只保留最近 3 条结果和一次 replan | 增加结构化轨迹摘要、失败模式记忆、跨回合检索和可淘汰的上下文；分别测试是否减少重复动作和无效重试 | 3–6 人周 |
| 跨平台统一动作 | 当前执行器主要面向 Windows/PyAutoGUI，本地模拟器只是评测替身 | 为 Windows、Linux、浏览器分别实现同一语义层的后端，处理 DPI、窗口坐标、键盘布局、剪贴板和无障碍树差异 | 4–8 人周 |
| 真实环境评测 | 只有 n=20 合成套件和待执行的 3 项人工桌面子集 | 接入 OSWorld/WebArena 一类可重置环境，固定镜像与 seeds，记录环境失败，至少多 seed 重复并给置信区间 | 4–8 人周，加环境维护 |
| 安全与提示注入 | 已有 dry-run、参数校验和逐动作确认，但没有独立沙箱或内容注入分类器 | 使用低权限 VM、网络 allowlist、秘密隔离、敏感动作策略和审计日志；对网页/图片提示注入做专门测试 | 3–6 人周 |
| 推理成本与延迟 | Qwen 推理占绝大多数单步时间；真实评测成功率仍低 | 先提升有效输出率，再评估更强基座、量化、缓存、批处理与小模型路由；同时报告延迟、显存和准确率 | 2–6 人周，取决于模型与硬件 |

优先级上，应先解决规划输出有效率和多步轨迹质量，再扩大真实环境评测；如果模型连结构化动作都无法稳定生成，单独优化 OCR 或执行器不会带来成比例的端到端收益。
